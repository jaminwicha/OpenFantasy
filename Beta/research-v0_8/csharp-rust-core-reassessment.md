# Core language reassessment: C#, Rust and the expanded world

Research date: 8 September 2026. This reassesses the 150-requirement design, including full-depth cities, mutable stacked terrain, independent Wait encounters, arbitrary historical access and branching. It complements [terrain/runtime research](terrain-runtime-and-worlds.md) and the [technical design](../spec-v1_0/TECHNICAL_DESIGN.md). No Beta performance benchmark, native integration prototype or platform export was executed for this paper. Numbers below are workload hypotheses or qualification criteria, never measured capacity.

## Recommendation and strongest countercase

**Keep portable C# as the selected authority for the first retained implementation, and close an explicit language qualification gate before broad dependent production.** This is a revised, conditional decision, not a claim that C# must outperform Rust or that native integration requires IPC. Godot C# remains the presentation layer in either candidate. The world should have one state owner, a compact data model and engine-independent commands regardless of its implementation language.

The strongest case for choosing **a whole Rust core now** is substantial: the core is still being established; world state and historical indexes may become large; compiler-checked ownership and the absence of a tracing collector in that core would reduce particular failure modes and improve control over allocation lifetime. A native core could also be embedded by other engines without requiring those hosts to adopt .NET. If retained workloads expose pervasive managed-memory costs, this early stage is the sensible time to change. The current evidence does not establish those costs, however, and the most consequential risks—causal scheduling, archive growth, history fidelity, combinatorial rules and understandable play—survive the language switch.

Neither frontier-model capability nor an agent's preferred language establishes correctness. Judge Codex and Claude through the same scenario fixtures, defect corrections, profiler captures and exported artifacts. A language should not be selected to flatter presumed agent talents. Artistic quality and world responsiveness require their own presentation/production proofs; a native simulation does not produce better sprites or choreography by itself.

## Three genuinely different implementations

| Candidate | State ownership and boundary | Main benefit | Main cost |
|---|---|---|---|
| Portable C# core | Core assemblies own state; Godot consumes projections in-process | Direct typed tooling and one language across host/adapters | Managed allocation and collection must be controlled and measured |
| Whole Rust core | Rust owns state, scheduler, transactions and history; C# calls coarse C ABI operations | Core lifetime control and stronger ownership/concurrency checks | Native packaging, ABI validation and debugging across runtimes |
| C# plus selected native kernels | C# owns authoritative state; Rust receives bounded immutable inputs and returns candidate results | Target a demonstrated expensive operation | Copies, ownership transitions and extra build artifacts can outweigh a small kernel |

The second option requires **no separate process, socket or IPC service**. A Rust library can expose C ABI entry points, and .NET can call native exports through P/Invoke. It also need not register every actor as a Godot extension object. The core can remain a plain library behind an opaque world handle. The third option must not become two writable inventories, two schedulers or two competing persistence systems. [Rust FFI documentation](https://doc.rust-lang.org/nomicon/ffi.html), [Microsoft native interoperability guidance](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices).

## What the languages actually guarantee

Rust's ownership model controls when owned values are released without a tracing garbage collector. References and borrowing constrain conflicting access in safe Rust. These are meaningful engineering advantages for region buffers, worker inputs and temporary reconstruction state. They do not imply that every Rust operation is allocation-free or has bounded latency: vector growth, allocators, reference counting, destructors and I/O remain work. [The Rust Book: ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html).

`Send` and `Sync` express whether values can cross or be shared across threads safely; unsafe implementations and foreign interfaces require additional review. They do not decide which of two valid purchases commits first, whether two inflows overfill a cell, or whether a newborn receives one identity after a retry. Those are domain invariants. C# safe managed code also provides memory safety; the difference is not “safe Rust versus inherently unsafe C#.” [Rust concurrency traits](https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html), [Microsoft GC fundamentals](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/fundamentals).

Determinism remains explicit in both candidates: checked integer arithmetic, exact rounding, canonical serialization, stable iteration, command ordering, versioned generators and domain-separated RNG. Rust's default `HashMap` is randomly seeded; its integer overflow checks depend on compilation configuration unless policy is made explicit. Simply translating a loop into Rust does not repair either issue. The selected contract's numeric and RNG golden vectors must match across debug/release, architectures and restart. [Rust HashMap](https://doc.rust-lang.org/std/collections/struct.HashMap.html), [Rust operator/overflow rules](https://doc.rust-lang.org/reference/expressions/operator-expr.html).

Parallelism should produce plans against immutable revisions and commit in deterministic order. Shared resources make superficially separate systems coupled. Factorio's developers describe why parallel electricity updates would change fuel use when networks share consumers, while other read-only work parallelizes successfully. This is evidence for dependency analysis, not a benchmark for either Beta language. [Factorio Friday Facts #421, 26 July 2024](https://www.factorio.com/blog/post/fff-421).

## Memory, CPU and the realistic workload

The proposed 20,000-resident city does not mean every resident must run a full decision tree at 20 Hz. That interpretation yields 400,000 actor decisions each second; trying 100 candidates each would mean 40 million candidate evaluations before terrain, persistence or rendering. These are arithmetic consequences of a hypothetical implementation, not necessary costs of actor parity. Full-depth saved identity can coexist with due-event scheduling, sparse relationships, bounded planning and detailed simulation where causally required.

Representation matters before language. Hypothetical resident records averaging 4 KiB occupy about 78 MiB for 20,000 residents; at 16 KiB they occupy about 313 MiB, before terrain, memories, indexes, definitions and projections. These are sizing probes, not complete actors. Duplicating the whole graph for every advancing branch multiplies costs in either language. Shared immutable definitions and persistent branch deltas should prevent gratuitous duplication without merging logically distinct lives.

C# can store hot components inline in arrays of value types, separate cold narrative records, reuse scratch buffers and pass spans/read-only references without constructing an object graph every tick. These techniques need attention to struct copying and aliasing. They do not require all data to become unmanaged, nor do they imply all structs live on the stack. Microsoft explicitly recommends measuring allocation hotspots before applying these transformations. [C# allocation and copying guidance](https://learn.microsoft.com/en-us/dotnet/csharp/advanced-topics/performance/).

Collection pauses are nevertheless real. Low-latency GC modes trade collection behavior against heap size and fragmentation; memory pressure can still force collection. “Turn on low latency” is not a no-pause guarantee. A Rust-owned core removes that core's tracing-collection burden, but the C# Godot presentation still allocates and can pause. A dedicated plain Rust host avoids managed execution there; that advantage does not automatically transfer to the complete client. [Microsoft GC latency modes](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/latency).

The 20 Hz scheduler has a 50 ms wall-time window. Report pure computation, allocation/collection, transaction durability, projection and queue delay separately. A fast average can hide disruptive tails. Staged excavation, path searches, historical preparation and support closure must also record backlog age and forward progress. Rust cannot rescue unbounded all-pairs cognition or a world that synchronously rebuilds every navigation layer after one mined cell.

## History and storage will not become cheap through Rust

Any-past-instant travel is primarily an archive and semantic-compatibility commitment. Both candidates require pinned same-instant commit boundaries, lossless lived event retention, versioned ancient-history refinement, immutable prepared prefixes and durable origin claims. Neither ordinary C# serialization nor deriving Rust serializers creates a stable multi-year archive contract. Wire/save formats must name fields, versions and ordering independently of object/struct memory layout.

At a hypothetical 256 bytes per retained event, 100 events each second produce about 92 MB per hour; 1,000 produce about 922 MB per hour, excluding indexes, checkpoints and redundancy. This argues for meaningful changes, compact encodings, incremental indexes and shared immutable history, not forgetting old states or recording a complete world snapshot every step. Record actual bytes per world hour and reconstruction cost during qualification. Do not claim that compression makes arbitrary lived history free.

SQLite's session extension illustrates a subtle trap: it coalesces repeated changes to a row and may omit a change subsequently undone. That is useful for final-state synchronization but cannot alone preserve every historical instant. Beta needs its own ordered semantic/delta archive in both languages; checkpoints accelerate lookup and never restrict destinations. [SQLite session extension](https://www.sqlite.org/sessionintro.html).

## A defensible Rust boundary, if evidence selects it

The candidate interface should contain `OpenWorld`, `SubmitBatch`, `AdvanceWork`, `ReadProjection`, `PrepareHistory`, `PollPreparation` and `CloseWorld`, with an ABI version and explicit status results. Only the core mutates authoritative state. Command IDs, expected revisions and durable receipts survive retries. Requests and responses use versioned bounded buffers; the renderer receives selected projections rather than the complete city every frame.

Use fixed-width integers, explicit byte lengths/encodings and opaque handles. Specify who allocates, retains and frees every buffer; no Rust `Vec`, managed object reference or borrowed actor pointer crosses as a public data structure. A C# `SafeHandle` can own native world handles, while source-generated `LibraryImport` keeps supported marshalling visible at build time. Measure serialization/copy volume and batch latency rather than quoting a generic per-call cost. [Native interop best practices](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices), [P/Invoke source generation](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke-source-generation).

Never unwind a Rust panic or C# exception across the interface. Return validation failures explicitly. An unexpected caught unwinding panic poisons the affected handle until recovery from the last durable commit; it must not continue with possibly partial state. `catch_unwind` cannot catch aborting panics. Process failure still requires the same journal/restart proof; in-process native code is not a fault-isolation boundary. [Rust FFI unwinding rules](https://doc.rust-lang.org/nomicon/ffi.html).

Avoid callback-heavy Rust-to-C# gameplay and per-actor FFI properties. Keep debugger symbols, correlation IDs and one reproducible command archive so a defect can be replayed in a standalone core harness. A small native kernel later can use the same discipline while returning candidate results for the C# authority to validate and commit. Do not build this boundary merely because it can be drawn elegantly.

## Godot, desktop, mobile and AOT

Godot 4.6 documents C# desktop support for Windows, Linux and macOS; Android and iOS remain experimental in that documentation, and C# web export is unsupported. Replacing only the simulation with Rust does not remove the C# front end's restrictions. A separate future non-C# adapter could exploit Rust portability, but that is a new qualified host, not a free consequence of compiling a library. [Godot 4.6 C# platform support](https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/index.html).

.NET Native AOT removes runtime JIT compilation and constrains dynamic loading/code generation; it retains runtime facilities rather than turning C# into a collector-free Rust equivalent. Its platform table is separate from Godot's export support. A successful standalone Native AOT executable does not prove the Godot client exports. Preserve AOT-compatible typed content operations and test the actual selected SDK, templates and dependencies. [Microsoft Native AOT deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/).

Rust documents supported desktop and mobile compilation targets, with different tier guarantees. Native outputs still need correct target architecture, system libraries, linker/signing configuration and export inclusion. .NET RIDs select native assets; Rust target triples are not interchangeable strings. A plain P/Invoke library needs explicit packaging, while a GDExtension has its own feature-tag library/dependency manifest. Validate whichever integration is actually chosen; do not introduce both. Device execution, suspend/resume and save recovery remain P14 mobile gates. [Rust target support](https://doc.rust-lang.org/rustc/platform-support.html), [.NET RID catalog](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog), [Godot extension manifests](https://docs.godotengine.org/en/4.6/tutorials/scripting/gdextension/gdextension_file.html).

## Selection gate and retained evidence

P00 records candidate hardware/OS/toolchain and language-neutral command, numeric, RNG, archive and projection fixtures. P01 implements the selected C# authority as real retained code. P01–P03 run these cases before broad P04 production:

1. **LANG-01:** 10,000-actor early fixture and separate 20,000-resident city profile, with 512 detailed actors/four active branches; record actual cognition, relationships, due work, memory and backlog. Population alone is insufficient workload specification.
2. **LANG-02:** terrain/support/fluid edits, encounter merges, market transactions and history preparation under simultaneous load. Report p50/p95/p99 step time against the 50 ms scheduler window and whether queues recover after bounded bursts.
3. **LANG-03:** sustained play/reconstruction captures allocation rate, GC pauses, heap/native memory, checkpoint/event bytes and restore latency; distinguish UI stalls, storage stalls and core work. Retain raw traces. [Microsoft dotnet-counters](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters).
4. **LANG-04:** replay equivalence across worker counts, architectures, release/debug and restart; retries, overflow and crash injection cannot change custody/history. Execute exported desktop clients and the standalone host.

All four cases are **unrun**. First repair expensive algorithms, data layout or allocation churn demonstrated by traces. If a remaining bottleneck is isolated, compare that bounded operation in Rust using the same retained inputs. Choose a whole Rust core before dependent bulk only if evidence shows pervasive managed-memory/latency costs, or a concrete embedding requirement that the C# design cannot meet, and native integration passes export, recovery and parity checks. A microbenchmark win alone is insufficient.

If the C# profile meets declared budgets with headroom, close the gate and proceed; do not maintain two complete cores. If neither meets them, revise scheduling/data representation or explicit workload qualification without deleting actor depth or history. Fixtures, content packages, import ledgers, schemas and diagnostics are retained across a justified change; language-specific implementation may require refactoring. “No throwaway code” means no disposable parallel game and no lost product work, not a promise that evidence will never require changing code.
