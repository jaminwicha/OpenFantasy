# Local session contract

`LocalWorldSession` takes ownership of a successfully admitted `SqliteWorldAuthority` and one current player control binding. Construction does not start game time: `SetReady(true)` enables selection. The current adapter is a trusted local-host profile, not network authentication. The authority must not be independently mutated or disposed after ownership transfers.

The host selects at nominal 50 ms monotonic deadlines. Late deadlines are discarded and the next deadline starts at least 50 ms after a stalled step finishes; there is no catch-up or offline simulation. Movement is one exact 32-subunit cardinal sample, or zero to stop, with a 150 ms freshness lease. Inputs never choose simulation elapsed time. Losing readiness clears movement. A step already selected at the cutoff may finish committing after readiness changes; later steps remain paused.

One player action can be pending. Identical bytes share its outcome, a different new request is explicitly refused while it is pending, and an exact durable retry can retrieve its previous receipt. Current delivery and actor control are checked before receipt access. Pending input is neither a receipt nor a durable acknowledgement. The task completes with a gameplay receipt only after `Commit` returns; stopping cancels pending input. A closed or failing backend faults `Completion` and pending work.

Current and historical occupied command identities are rejected before selection. A private preview catches further command/result/spawn selection conflicts. Such a request faults with `AuthorityDispatchException`; an ordinary step is rebuilt with a fresh host cause and the other selected movement. Held interactions have no empty fallback commit. Storage/IO failures and `WorldRecoveryLimitException` stop and fault the session; they are never converted into gameplay receipts or hidden by idle fallback.

An advancing step resolves actions first. If an action opens a dialogue, that already-selected step still contributes one ordinary calendar/exposure increment while movement is suppressed. A held batch selects actions only and contributes no clock time, including the close that releases the final hold.

`LocalNpcController.PolicyVersion` is `local.home-amble.v1`, a newly authored implementation policy. SHA-256 input is that exact ASCII domain followed by fixed-width world ID, actor ID and unsigned cycle ordinal. Each 64-step cycle admits up to 16 movement samples followed by 48 idle steps; the direction is the digest's first byte modulo four. Proposed feet remain within the exact XY home-radius circle. Current actor bindings, full body clearance, support and occupied space are still adjudicated by the same world processor used for player movement. This is finite home amble, not a claim that the original NPC's psychology or schedules have been migrated. The source version and implementation hashes belong to the coordinated build evidence. Changing the policy for ongoing worlds requires future explicit compatibility/migration rules.

Accepted movement samples are journaled. Recovery replays those samples rather than rerunning the NPC controller. Rendering supplies no NPC decisions or world truth.

`LocalWorldView` is an immutable cached projection. This admitted local profile is sight-complete; its actors' names, positions, presence revisions and controller kinds are visible. Only the selected player's own counted lots and storage revision/quantity, and their addressed active dialogue, are included. NPC inventories, source claims, commit sequence, state hashes and storage diagnostics are excluded. This is a bounded local projection, not the future world's global knowledge/visibility system. Profile-four progression and quest terms are projected from admitted authority state as described below. Food consumption, injury healing and exposure-driven aging remain pending.

The internal `TimeProvider` constructor is the monotonic host-clock seam used for controlled pacing and input-lease tests. It changes host scheduling only and never supplies game time to the core.

## Gathering profile connection

The session selects the persisted `WorldSnapshot.ProfileVersion` for every batch, including movement-only steps. Pending request comparison uses the strict actor-action codec dispatcher, so the existing exact v1 actions and new gathering actions retain their own original bytes without acquiring separate retry namespaces. The shared authority dispatches known snapshot/batch versions during admission, commit and full replay. Receipt v1 remains unchanged. None of this migrates an existing save or adds gathering state to a legacy world.

Gathering remains one semantic actor request through the same bounded pending slot and durable cutoff. Only the core adjudicates a swing and its effort, source and custody changes. The ordinary accepted step advances work once. A held interaction cannot gather or accrue work, and a paused or unopened session supplies no steps or offline regrowth. Repeated identical requests share one eventual result and exact committed retries add no further swing.

`GatheringNodes` contains the visible Ready/Stump nodes of this sight-complete locality; Absent nodes are omitted until their committed state becomes visible again. Each row exposes its admitted identity, name, anchor, node revision, kind, required tool category, remaining swings and visual phase. It does not expose finite source capacity, issued cursor or regeneration scheduling internals. `GatheringTools` joins only the controlled player's actual inventory lots to exact admitted tool definitions; it exposes lot/revision, category and power. `PlayerGatherEffort` is only that actor's current bounded effort, and is null for legacy worlds. These are presentation affordances, not new permissions or eligibility guarantees; current body, ownership, reach, reservation and capacity checks remain authoritative.

## Production and quest profile connection

The same serialized action slot and step authority own crafting and quest actions. Old action and receipt bytes remain unchanged; explicit dispatch admits only actions supported by the saved profile. The production view includes the selected actor’s own raw/derived lots and craft eligibility. Its shared production revision is still a global concurrency token: this is not a claim of general cross-actor noninterference or fair simultaneous crafting.

`Progression` contains only the selected actor’s admitted class name, level, residual XP, HP/MP and gil balance/revision. `Quests` includes that actor’s retained participations and the current addressed giver’s available offer. It exposes public promise/reward terms and current eligibility, without reserve/account/project-storage identities, private balances or another actor’s progress. Current admission has one offer per giver; a future multi-offer profile requires explicit UI selection.

`AvailableForDelivery` excludes protected/reserved raw lots from the client’s proposed six-wood selection. `FarmQuestActions` selects deterministic lot prefixes from the current public view; it cannot choose the reward or credit prior gifts. Core rechecks ownership, exact pins/revisions, current addressed dialogue, reach, body functions, reservations and funding. Accepting reserves an obligation; completing atomically moves and reserves real raw units and applies the source-pinned reward. Exact retries and repeated completed offers cannot pay twice. Dialogue remains held throughout acceptance/delivery and contributes no advancing work or time.

Save selection and profile migration precede session ownership. Existing valid quest destinations win; new admissions use a verified copy of progressed production state and retain their predecessor. An absent destination cannot bypass an existing gathered source merely because no intermediate production destination was supplied. No client-generated fresh world replaces incomplete or incompatible source files.
