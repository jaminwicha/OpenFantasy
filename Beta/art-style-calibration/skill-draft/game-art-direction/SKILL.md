# Game Art Direction

Read the project's art brief and acceptance record before creating production assets. Keep project-specific references, palettes, dimensions, and aesthetic choices in the project, not in this shared skill.

## Ownership

When the project calls for dedicated artist agents, give the art role ownership of reference interpretation, asset generation, pixel cleanup, animation, visual consistency, and editable art sources. Engine builders own runtime integration and behavior. Either capable model can fill either role. Honor current delegation permissions; this skill alone does not authorize spawning agents.

Agree on the artifact contract at the boundary: native dimensions, perspective, pivots, direction order, animation names/timing, source format, exports, and style version. Do not alter simulation or engine architecture to accommodate an accidental generator convention.

## Calibration and acceptance

Separate a proposed style from an accepted reference and from a validated production asset. A generated contact sheet can communicate visual direction without proving native pixel dimensions, usable animation, tiling, alpha, or editability.

If the user requires style acceptance, create a small representative proposal and record the user's actual acceptance, reference version, and scope before mass production. Do not infer acceptance from silence or the agent's own review. Reuse existing acceptance for conforming work; reopen it only for material drift or a new visual requirement. Keep independent engineering work moving with identified placeholders.

Calibrate the asset categories that must coexist. For pixel-art games, compare native-size and integer-zoom specimens and inspect moving assets in the target renderer. Check pixel-grid discipline, silhouette, perspective, material ramps, alpha, pivots, temporal identity, seams, and camera stability as relevant. A palette/grid check measures file properties, not artistic merit.

When feedback identifies visual overload, reduce decorative density selectively while preserving
craftsmanship, identity and the intended fidelity. Use quiet areas and a few meaningful focal
details. Do not equate higher quality with more ornament, texture or glow, or respond by
globally lowering resolution or erasing the historical/gameplay cues the user values.

## Tool selection

Discover callable tools before promising a workflow. Distinguish a verified integration from documentation, a local install from a connected tool, and a style-oriented generator from an exact editor/exporter. Prefer primary documentation and the actual schema for mode-specific controls; stronger modes may ignore parameters supported by simpler modes.

Follow the active image-generation and editing tool rules. Choose a pixel editor or specialized generator when available and appropriate to the authorized task. Do not substitute code-drawn placeholders for requested generated art. Do not buy subscriptions, install integrations, or incur external generation costs solely because a candidate appears in documentation.

Evaluate a candidate on a small fixed asset brief and accepted references. Include cleanup, rejected generations, editable-source quality, and actual-engine playback in the comparison. Prefer the least cumbersome toolchain that reliably produces accepted art; tool count and vendor claims do not establish quality.

## Delivery

Preserve the project-bound output and usable editable source when supported. Deliver native exports, animation metadata, a visual preview, the accepted-style version, generation/edit provenance, and remaining limitations. Label proposals, placeholders, accepted art, and validated production assets accurately. Keep engine-import feedback and art-style feedback distinct so each owner can address the actual defect.

## Preserved options

When the user likes a direction and requests a richer or otherwise different option, preserve
the prior files and positive preference explicitly. Create a sibling variant using consistent
subjects/composition where useful for comparison. Record the actual scope: liking an option
does not automatically select it for production, and considering another option does not
revoke the earlier preference. Do not repeatedly ask the user to endorse what they already
endorsed. Keep project-specific style names and detail levels in the project records.

## History, changing conditions and gameplay

When the art brief calls for accumulated history, express use, repair, inheritance and
adaptation through material-specific details. Distinguish age from neglect; a cared-for old
object can work well. Preserve readable silhouettes and routes rather than adding texture
noise or decoration everywhere. Keep exact fictional histories in project records.

When light, weather, seasons or wear changes during play, collaborate with design and engine
owners on semantic state, artist-authored variants, masks/layers and transition behavior.
Calibrate representative conditions and motion before multiplying every asset into every
combination. Tie consequential cues to actual simulated state and appropriate player
responses; the renderer cannot invent damage or repairs. Separate cosmetic atmosphere,
inspectable historical facts and functional condition.
