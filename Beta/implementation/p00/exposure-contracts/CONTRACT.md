# Experienced duration and exact fractional progress

9 September 2026. P00 arithmetic boundaries for RQ-016/073/076/099/105/126/127/174 and later growth, wear, need and injury processes. These immutable values separate **experienced time** from a person's calendar destination, commit revision or client clock. They do not implement actual Wait admission, rest, biological aging, offline policy, effects, scheduling or historical transit.

`LocalExposureDuration` uses nonnegative UInt64 days plus normalized milliseconds 0..86,399,999, with UInt128 total-millisecond arithmetic. This permits eon-scale experienced durations without compressing them into a signed 64-bit millisecond timestamp. Addition is checked and rejects unrepresentable accumulated days. No constructor or subtraction converts a `WorldInstant` into experience. Its explicit JSON constructor protects the nonzero immutable value from the default-struct reset pitfall; JSON remains diagnostic, not the authority's canonical save format.

`ExposurePacingV1` encodes the already selected initial pacing: each **accepted advancing exploration step** contributes 1800 experienced/world milliseconds; each accepted tactical readiness unit contributes 10 local exposure milliseconds. Thus 48,000 normal exploration steps span one world day, and 100 tactical units span one local second. At the existing 20 Hz exploration profile this is the 40-minute day. The caller supplies only advancing units. Held, offline or unaccepted work contributes zero. These helpers neither observe wall time nor keep uncredited backlog; they cannot retroactively turn time spent held into progress. Actual coupled-domain admission, consent, interval ownership and profile selection must establish which progress was accepted before calling them.

`ExposureRate` pins the output-unit identity, rule-version hash, nonnegative numerator and positive denominator: output units per experienced millisecond. `ExposureProgress.Begin` starts one subject at zero under that immutable rate. `Advance` returns a new value with accumulated experience, whole credited units and fractional remainder; the original remains unchanged. Zero exposure returns the same value. A zero numerator still records experienced time while crediting no units. The rate cannot silently switch during a progress record.

For input milliseconds `d`, numerator `n`, denominator `q` and prior remainder `r`, credited units are `floor((d*n+r)/q)` and new remainder is `(d*n+r) mod q`. The implementation divides first: `(d/q)*n + floor(((d%q)*n+r)/q)`. This preserves exact UInt128 checked intermediates even for huge low-rate intervals. Output units remain a checked UInt64 counter, and unrepresentable output or elapsed time rejects before returning a candidate. The caller must stage a supported wider/chunked process or reject; it cannot drop overflow or clamp progress silently.

Capture retains the subject, full immutable rate, elapsed duration, credited total and remainder. Restore requires the explicitly expected rate to match, then recomputes the exact cumulative total/remainder from elapsed time. Altered counts, carry, denominator, unit or rule version reject. Because Begin is zero and no reset/rate-switch API exists, this local algebraic consistency is provable; it does not establish the truth of the supplied subject/history. Captured records are metadata and do not authorize effects or resolve duplicate accepted intervals.

The canonical `exposure.progress.v1` frame contains subject ID, output-unit ID, full 32-byte rules hash, numerator, denominator, elapsed days, milliseconds within day, completed units and remainder, in that order with existing core framing.
