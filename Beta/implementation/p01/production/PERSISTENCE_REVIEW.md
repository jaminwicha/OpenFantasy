# Crafting save continuity

10 September 2026 UTC. Bounded inspection of the schema-2 world store, profiles 1/2, source admission, local session and the incoming production contract. The coordinator subsequently assigned the Hosting implementation below to this reviewer. This document is a design recommendation and implementation contract, not independent qualification of that implementation. No managed build or native migration test had run when this recommendation was written.

## Decision

Preserve the actual gathering world and its complete journal. Add a pinned world profile 3 containing production definitions and actual production state, an explicit migration journal kind, and an exact SQLite schema 3. Upgrade a consistent copy and publish it only after validation; retain the original save. Do not reconstruct a fresh eight-wood farm, reinterpret old Give commands as quest submissions, or silently drop old receipts.

This follows [TDD §4](../../../spec-v1_1/TECHNICAL_DESIGN.md#4-transactions-saves-and-recovery), which requires migration on a copy and atomic selection after validation. The earlier [gathering review](../gather-craft/PERSISTENCE_REVIEW.md) deliberately deferred real migration; this increment supplies that specific boundary. Same journal means the same retained history and identities, not a requirement to replace a live SQLite filename in place.

## Existing constraints that matter

- `world_commits.kind` accepts only advancing step 1 and held interaction 2. Recovery currently decodes every row as a `WorldStepBatch`. A migration cannot masquerade as either gameplay kind.
- `world_occupied_identity.kind` accepts cause 1, command 2, result 3 and spawned entity 4. Newly admitted recipe/material definitions require a truthful additional role, proposed as admitted definition 5.
- Every table definition and implicit index is admitted by exact SQL text. Changing a `CHECK` is a real schema change. Unknown versions, extra triggers/views, malformed rows and broken references must continue to fail closed.
- Snapshot, command and batch versions are separate. Existing action-v1 Speak/Give/Close and action-v2 Gather bytes, hashes, receipts and replay behavior remain unchanged. Profiles 1/2 retain their original codecs and rules. A new production action and profile-3 batch are explicitly dispatched.
- Receipts are keyed by principal plus command ID, independently of profile version. `FindReceipt` already checks current control before returning an exact older command's receipt. Migration preserves that table and its immutable request bytes; it must not require the old request to be newly legal under profile 3.
- Genesis, every historical row, checkpoints, raw-source budgets, issued cursors, intervals, actor/control identities, calendar, effort, movement and active dialogue are retained. Migration advances only the commit revision, once. Inventory and production revisions have distinct meanings; neither is reset to the world revision.

## Concrete boundaries

The accepted Core boundary is `WorldProductionMigration` plus `WorldProductionMigrationProcessor` and `WorldProductionMigrationCodecV1`. The request binds a fresh cause ID, world/branch, exact current commit revision and advancing-step count, exact old head hash, source admission version, derived target admission version and the new `ProductionSnapshot`. Its production state starts at revision zero, with pinned recipes/material bindings, no batches and no transformed lots. Output supply does not exist until an actual craft commits.

The target admission version is derived canonically from the source admission version and exact production bytes. It cannot arbitrarily repin the old world. Existing item definitions are reused only with their exact pins. The migration decision returns the candidate root and sorted newly admitted definition IDs; replay recreates and compares its canonical outcome. The bounded migration frame fits the existing 256 KiB accepted-input and outcome columns. No actor-command receipt is fabricated for this privileged host operation.

The source owner supplies historical occupied IDs as well as current/genesis identities. Newly admitted definitions remain occupied even if a later feature removes them from current state. Actor, custodian and existing item references are references, not newly created identities. The migration cause is globally fresh. A collision rejects the upgrade; it does not silently choose a different identity or reinterpret another entity.

The smallest Hosting entry point is an explicit copy-and-publish operation accepting source path, fresh destination path and the pinned migration request. Ordinary `OpenExisting` continues to open/replay known formats without upgrading. It supports exact schema 2 and exact schema 3. Profile-1/2 creation retains schema 2; profile-3 creation uses schema 3. World profile and physical schema are admitted separately.

## Copy, transform, verify, publish

1. Require distinct source/destination paths and a destination that does not exist. Acquire the original source's exclusive SQLite lease, admit exact schema 2 and recover its entire journal. Compare the request's old-head hash/revision/pins with this actual state. A running `LocalWorldSession` must first stop; pausing UI input alone is not sufficient ownership transfer.
2. Use SQLite's backup operation into a fresh sibling staging database. The original remains the backup. Reopen and fully replay the staging copy, comparing the exact genesis/head, every prior receipt, identity and journal row through recovery. Do not use `File.Copy` on an active WAL main file. Microsoft exposes this operation as `SqliteConnection.BackupDatabase`. [Microsoft documentation](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/backup).
3. On the exclusively owned staging connection, prepare the complete pure migration candidate before writes. Within one schema-change transaction, install exact schema 3, append migration kind 3, reserve the cause and added definitions, update the head, and write any checkpoint required by the unchanged checkpoint policy. Advance journal byte/commit budgets without resetting their prior usage. Source data is never modified by this transaction.
4. Reenable and verify normal foreign-key enforcement, validate exact schema 3, then replay the entire candidate journal from the original profile-2 genesis through the migration and any later profile-3 rows. Verify canonical outcomes, hashes, command table, identity table and checkpoints exactly. Checkpoint-tail acceleration remains unqualified; a new checkpoint is not permission to skip old history.
5. Checkpoint and close the staging database so its final main file contains all committed data and has no required WAL sidecar. Publish to the absent destination in the same directory/filesystem using a no-overwrite operation. No simulation session or player projection runs before this succeeds. Keep the source as a clearly identified recovery copy; normal startup selects the destination after success and never silently falls back to an older source when a newer save is corrupt.

An error before publication leaves the original usable and no accepted destination. An error after publication has an uncertain return, not an uncertain world: reopening the destination must recover the one migration. A repeated explicit upgrade must refuse to overwrite a destination; the caller can reopen and verify the already published continuation. Continuing both the original and upgraded copy as separate games requires an explicit fork policy; neither a filename nor a backup grants that policy.

For the first implementation, a new destination path is sufficient because it carries all existing progress. A stable save selector and crash-qualified same-path replacement are separate future ergonomics, not reasons to reset progress now. Directory-entry persistence across abrupt hardware failure still depends on filesystem/OS guarantees and needs its own platform evidence; process-kill success alone is narrower.

## Exact schema evolution

SQLite documents a safe table rebuild: disable foreign keys before the transaction, create the replacement, copy rows, drop the original, rename the replacement, check foreign keys, commit, and reenable enforcement. Renaming the original first can rewrite dependent references incorrectly. Use this only inside the isolated migration adapter, with normal authority paused; do not expose general schema editing or weaken ordinary admission. [SQLite schema-change procedure](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes).

A small read-only-to-repository experiment instantiated all six current table definitions in an in-memory Python SQLite 3.53.1 database, with a commit key above `Int64.MaxValue` and dependent receipt/identity rows. The documented rebuild preserved exact row bytes, implicit indexes and foreign-key relationships. SQLite emitted a quoted final table name after rename: `CREATE TABLE "world_commits"`. Exact schema-3 creation/admission must deliberately use that same text. The production native library is pinned separately to SQLite 3.53.4; this design experiment is not its qualification.

Schema 3 changes only explicit journal/identity kind constraints and their necessary canonical SQL definitions. The unchanged BLOB length/type checks, unsigned big-endian counters, singleton rows, bounds and foreign keys remain. No `writable_schema`, catch-and-reset fallback, arbitrary migrations registry or generic event bus is needed.

## Crafting conservation and compatibility

The worker's production model uses immutable `ProductionBatch` provenance and `ProductionOutputInterval(batchId, outputIndex, start, end)`. Outputs are not minted as another `AdmittedCountedSource`. Consumed raw intervals remain as retirement claims and must not overlap live raw lots; gathered retirement ends remain bounded by their actual monotonically issued node cursor. Production definitions and physical calibration pins are persistent, not recomputed from current shipped balance data during replay.

The source recipe `craft_rations` consumes two berries and one wood to produce two rations. An instantaneous recipe denotes one accepted operation, not an invented number of elapsed work ticks. A successful craft atomically retires the exact owned inputs, creates the actual output batch/lots, updates storage/accounting and records the receipt. Capacity is evaluated against the final combined raw/transformed inventory. Partial input use, rejected/full-pack actions, retries and crashes must preserve conservation. Future timed jobs may add their actual reservation/progress records without changing these historical instant operations.

The existing client builds today's genesis before opening a save and compares its world/admission IDs. That startup assumption must change for upgraded worlds: retain the original world ID, accept the actual supported admission chain, and derive local actors/items from the recovered root. A newly generated profile-3 world may have a different seed namespace; that cannot become a reason to reject or regenerate a valid upgraded profile-2 world. Start `LocalWorldSession` only after migration, content validation and all fallible startup lookups finish. Its batch constructor then reads the committed root's current profile version.

## Required evidence before claiming continuity

| Boundary | Required retained case |
| --- | --- |
| Old formats | Existing v1/v2 golden bytes and actual old save fixtures still open, replay and continue under their original rules. Their past bytes and receipts remain identical. |
| Real progress | Gather, deplete, transfer and create a held dialogue before upgrade; verify the migrated calendar, effort, node cursors, lots, owners, dialogue, controls and historical keys exactly. Migration contributes one commit and zero steps. |
| Actual production | Craft from partially used old/raw lots after migration, reopen and retry the exact command. Verify one retirement/output batch, correct final combined capacity and no invented raw source allowance. |
| Migration collisions | Wrong source/head/admission, reused cause, definition collision or malformed production input rejects before publication. A higher codec version cannot be smuggled into an old batch. |
| Hostile storage | Modified schema, altered migration bytes/outcome/hash, missing/extra definition occupancy, removed old receipt, forged new head, missing/unscheduled checkpoint and invalid kind/profile transitions fail replay. |
| Interruption | Fault before/after staged COMMIT and before/after destination publication; original remains openable, accepted destination contains exactly one migration, and recovery never falls back silently. |
| SQL mechanics | Pinned native table rebuild with real old rows, values above signed 64-bit range, preserved foreign keys, exact schemas/indexes, transactional rollback and restored enforcement. |
| Ownership | Competing original owner refuses upgrade; existing destination is not overwritten; staging cannot become a running session; all failure paths release their leases. |
| Limits | Migration counts old journal usage plus its own bytes/commit. Measure backup, transformation, full replay, output file size and peak memory on an actual gathered save, not only an empty world. |

The existing development envelope remains 250,000 commits, 65,536 receipts and 128 MiB accepted journal bytes. At continuous 20 Hz the commit cap is about 3.47 active hours. Production history also grows the canonical root; retaining retirement provenance while serializing the full root every step needs measurement and a later retained storage optimization. None of these limits are a production-scale save guarantee, and migration must not erase history to avoid them.

## Implementation outcome

The coordinator accepted this design and assigned its Hosting implementation to this reviewer. The implemented public entry point is `SqliteWorldAuthority.UpgradeGatheringToProduction(sourcePath, destinationPath, WorldProductionMigration request)`, returning a reopened authority only after publication. It preserves exact schema-2 support, uses the narrow schema-3 changes above, and retains a failed private staging directory for diagnosis without selecting it. The shared connection lease retains its original single-version API for the separate counted authority and adds only the known world-schema 2/3 opening and bounded migration/backup methods.

On 10 September 2026 at 03:20 UTC, the pinned Debug build and all **143 Hosting tests passed**, including 108 prior cases, 21 author-owned migration/storage cases and 14 independently authored content cases. The tiny gathered-save migration retained 103 old commits/steps and took 965.946 ms inside the concurrent test suite. See [the complete scoped results](hosting-validation/RESULTS.md), [TRX](hosting-validation/test-results/production-hosting-debug-initial.trx) and [exact source/output manifest](hosting-validation/VALIDATION.json). This is implementer verification; it does not turn the initial critic recommendation into independent approval of the resulting Hosting code.

A separate read-only inspection of the coordinator's `FarmSaveOpener`, `FarmClientSession`, `FarmProductionProbe`, input handlers and native checker found no new startup lease/session defect. The source selection is rechecked after exclusive reacquisition, current destination failure does not silently fall back, and fallible content/control lookups precede live-session creation. The probe requires actual production revision and output counts, so a dropped craft input cannot pass as a craft. Two bounded improvements were sent to the coordinator: distinguish input dispatch from pending/completed state to avoid a premature harness failure, and describe its JSON comparisons as selected retained projection fields, because they are not a complete canonical-world comparison. Native execution belongs to the coordinator's separate evidence.

## Independent sidecar finding and correction

The independent Hosting critic subsequently demonstrated that an absent destination main file can still have a valid orphan WAL, and SQLite can recover that unrelated WAL over a newly published candidate. The initial main-file-only publication guard was therefore insufficient; the preceding 143-case result did not cover this risk.

The shared fresh-file admission now checks the main path and `-wal`, `-shm`, `-journal` paths, rejecting existing files or directories without consuming them. This applies before ordinary new-world creation, the retained counted-authority creation, backup creation, upgrade entry and immediately before the no-overwrite publication move, after the fault seam. The critic statically reviewed the correction. Fourteen added cases preserve existing sidecars, inject them immediately before publication and include an actual unsafe control reproducing orphan-WAL replacement on the pinned native SQLite 3.53.4 library. The guard then rejects that exact WAL unchanged. The corrected complete Hosting suite passed **157/157**; [retained evidence](hosting-validation/SIDECAR_VALIDATION.json) supersedes the earlier source qualification without rewriting its history.
