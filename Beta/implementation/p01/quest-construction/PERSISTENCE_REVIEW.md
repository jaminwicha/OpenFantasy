# Quest, reward and construction continuity

10 September 2026 UTC. Independent bounded architecture/persistence inspection before the quest implementation. Runtime files were read only and no builds were run for this recommendation. The coordinator owns quest/world/client integration, the progression worker owns actor statistics and reward transitions, and the source worker owns import/admission evidence. Later implementation review and executed tests must be identified separately.

## Retain schema 3; introduce world profile 4

The existing physical schema already admits gameplay kinds 1/2, migration kind 3 and historical identity roles 1–5. A quest/progression profile therefore does **not** require SQLite schema 4 when it fits the current byte bounds and identity roles. Use kind 3 with a closed, strict dispatch over the existing `world.production-migration` version 1 and a new quest-migration tag/version. Preserve the exact old tag, payload, outcome and interpreter. The internal enum name can become `ProfileMigration`; its persisted value remains 3. This is a concrete two-case dispatcher, not an open event bus or a parser that falls back after a decoding error.

Profiles 1/2/3 retain their exact snapshot, batch and action bytes and replay behavior. A profile-4 snapshot adds actual quests, conserved currency and actor progression; profile-4 batches pin the new rules even when they contain only movement or no action. New accept/turn-in commands use explicit versioned frames, while old actions retain their original frames and meaning. Ordinary Give cannot become a quest claim after this update. Existing crafting retirement histories, output lots, recipe pins, source budgets/cursors and receipts remain intact.

The current recovery code has two specific checks to update: schema-3 genesis/head admission currently names profile 3 only, and every migration row is decoded directly as a production migration. Replace these with explicit known profile/tag cases. Do not loosen admission to any numeric version greater than three. Recovery still begins at the actual original genesis, which can be profile 2 followed by production migration and then quest migration; it must reproduce all intermediate hashes and old checkpoints.

The new copy upgrade can reuse verified backup comparison, full replay, journal policy, file-set guards and closed-file publication. A schema-3/profile-3 source needs an ordinary foreign-key-enforced transaction to append its quest migration, identities and new head. It does not need the earlier table rebuild, temporary foreign-key disabling or a `user_version` change. The existing profile-2→3 upgrade remains supported exactly.

## Exact migration boundary

Use a pinned `WorldQuestMigration` request containing a fresh cause, exact world/branch, expected root revision and advancing steps, exact old head hash, source admission version, and the complete new quest/currency/progression admission. Derive the target admission version from those canonical additions and the source pin. The input must describe an initial quest ledger, explicit initial actor progression and finite currency funding; it may not silently include a completed quest or spent reward.

The candidate advances the world commit revision by one and retains advancing steps, calendar, exposure, current actor forms/injuries, existing dialogue, gathered nodes, production state, old custody and controls. If a real new project storage is admitted, it is explicitly additive and starts empty, with a declared owner, receiving policy, capacity and reservation identity. Existing storages, lots and source allowances are not recreated. The new currency supply is a declared bounded admission event, not an increase hidden in an actor's balance.

Keep identity distinctions: new definitions use retained role 5; new quest instances, project custodians/reservations, currency accounts and funding records use the appropriate existing instance role and are checked against current, genesis and historically occupied IDs. References to an existing actor, item or source do not create another identity. A migration result should return both added definitions and added instances with their roles so the store reserves every new persistent identity. The migration cause remains role 1. No actor command or receipt is invented for the privileged admission operation.

Copy/publish retains the [qualified sidecar boundary](../production/hosting-validation/RESULTS.md): source ownership, consistent backup, exact old rows, complete candidate replay, source preservation, and refusal of main/WAL/SHM/rollback-journal paths both at entry and immediately before publication. Unknown/corrupt current destinations must not fall back to an older production save. An explicit same-world continuation is selected only after success; continuing the original and new copy independently would require a fork policy.

All old journal usage and checkpoint counters carry forward. Migration does not buy another 250,000 commits by resetting revision, discard receipts, or introduce a checkpoint that permits historical rows to be skipped. It also must not become a new 20 Hz clock owner; construct `LocalWorldSession` only after migration and all fallible startup validation finish.

## Source findings and funding

The retained quest record is `openfantasy.aldermere:quests/wren_orchard`, source `/quests/44`, payload SHA-256 `bbb996bb2ca6ca4e27b942f7f40f9ea624813909e037ec86980ed8aaa4ab86cb`: minimum level 1, six original wood, 420 XP, 200 gil, no item reward and no prerequisite list. See [the preserved source payload](../../../Runtime/content/legacy/aldermere-first-loop/records.json). Source code inspection by the content/progression workers found that a new player begins at level 1, XP 0 and gil 0; Wren's absent gil initializer likewise means 0. Source completion removed the six wood and directly increased player gil. It did not debit Wren's cash or build the windbreak.

Therefore a 200-gil reward reserve is an **authored funding correction**, not imported Wren pocket money. The accepted direction is a small separate conserved currency ledger: pinned currency, finite admitted supply and the complete bounded account balances. Initialize the declared quest reserve to 200 and character balances to their admitted values. The total supply remains balanced. Currency has no physical coin mass or backpack-slot claim in this increment. Exact transfers are recoverable from the world journal; a duplicate unbounded transfer history inside every snapshot is unnecessary.

Fund acceptance, not just completion. A single reserve of 200 cannot promise two unconditional rewards of 200. Acceptance either allocates a per-claimant escrow or records an exact unpaid obligation against the remaining reserve. The invariant is that reserve balance covers all accepted, unpaid obligations. Completion discharges the claimant's obligation while debiting the reserve and crediting that actor. Another acceptance fails when the uncommitted funding capacity is exhausted. Cancellation, actor death and escrow refund need their own later transitions; an accepted obligation cannot simply disappear because an actor leaves the active screen.

The current one-player admission can fund one reward. Two/four-actor tests must explicitly admit 400/800 gil, or an equivalent independently justified budget, before claiming those actors can all accept and finish. Do not mint 200 per actor on demand, present a single-player reserve as complete co-op funding, or disclose other actors' balances/obligations through the player projection.

XP is progression evidence, not transferable money. Completion applies the exact pinned `ActorRewardDefinition` once, with checked level/residual-XP/stat transitions. Class, heritage and growth pins are persistent. Wren's source statistics are classless and minimal; assigning Squire growth or restoring untracked statistics during migration requires explicit admission, not an assumption inferred from a humanoid sprite. Existing body injury/condition state must not be healed merely because a newly introduced HP field starts at its authored value.

## One atomic raw-wood delivery

Use an explicit quest acceptance followed by an explicit turn-in. Per-actor quest-entry revisions such as absent 0, accepted 1 and completed 2 avoid unrelated actors conflicting on one public global quest revision. The internal complete ledger can still advance its global revision. The single serialized authority adjudicates shared funds and project capacity against its current candidate; actor commands need not expose or depend on other actors' private currency/quest changes.

For the first delivery contract, support **raw source lots only**. A selection binds lot ID, expected lot revision and positive quantity, and the operation requires the exact original wood definition/version. A transformed-lot ID rejects. Future acceptance of derived wood requires an explicit provenance-family selection retaining its actual production interval; it must never be converted into an invented raw source claim.

Transfer exactly six current eligible source units into the dedicated Wren/project custodian, preserving every source ID and interval. Do not remove them into a fake production batch. The project storage avoids filling Wren's personal backpack with quest materials and provides a real bridge to construction. Apply the admitted project reservation to delivered lots. Otherwise Wren could withdraw them through ordinary Give before construction, and completion could not truthfully promise the stock remains available. The construction operation later consumes or relocates only the material reserved for that actual project.

The existing single-lot transfer planner always derives its partial child at `DeriveSpawned(commandId, 0)`. Calling it repeatedly under one command ID would alias multiple partial splits. The approved composite planner must sort explicit selected lots, assign distinct split ordinals, preserve full-lot IDs and each interval, and check every resulting identity against current/genesis/historical occupancy. Each touched lot advances its revision; touched storages and custody advance once for the compound command. Do not synthesize fake accepted subcommands solely to get different split IDs.

Before accepting any candidate, check current control, the pinned giver/offer, reach and applicable body/communication functions, level/eligibility, the actor's accepted quest-entry revision, source ownership and exact revisions, protected/reserved flags, exactly six eligible wood, destination receiving permission and final combined raw/transformed capacity. Also preflight the funded reward, progression overflow/limits, all spawn/result identities and the ledger bounds. Then commit delivery, project reservation, completion, debit/credit, XP/stat result, receipt and identity reservations together. Failure returns a terminal rejection without delivering wood or spending money; it must not leave a completed quest with an unpaid reward.

A menu acceptance/turn-in can use the existing held-interaction semantics if explicitly allowed: no elapsed clock, plant regrowth, work effort or retrospective exposure is added. Actual construction work is a different action and must use its own admitted time/work rules. Earlier ordinary gifts do not count retroactively, and simply possessing Wren's requested item does not imply the actor accepted the quest.

## Construction boundary that follows

Quest completion means a fulfilled supply agreement. A changed sentence or windbreak sprite is not a constructed structure. Preserve the original narrative as source evidence and choose truthful present-tense dialogue for a project that is funded/material-ready but not yet built; show the finished protection only after the construction transition exists.

The construction increment needs an actual stable structure identity, pinned form/material definition, admitted footprint/height/support, persistent material provenance and condition, plus the matching spatial collision/support change. Preflight occupied actors, access and support before committing. Marking a quest complete must not silently alter terrain or seal a route. Reservation ownership must prevent ordinary inventory operations from removing structural materials without the corresponding dismantle/damage transition.

Two truthful material models remain available: retain the claimed raw intervals in a protected structure-material custodian, or perform a declared production transform into traced structural parts. Either can reuse existing identity/custody/production machinery. Do not consume wood by deleting the last claim, call it waste when it became a wall, or create output supply rights disconnected from the inputs. Choose the actual construction representation when its geometry and interaction operation are implemented; a placeholder construction service would not prove it.

An old finite save may have exhausted its obtainable raw wood before quest admission. Preserve that progress honestly; do not silently reset source cursors or increase source capacity to make the new task solvable. If the prototype promises a finishable newly introduced quest in every upgraded save, it needs a real additional resource/recovery admission or a checked advancement witness. This is distinct from funding the reward and should remain visible as a preparation constraint.

## Initial implementation inspection

10 September 2026 UTC, before the profile-4 composition and coordinated build. This is a static inspection of the newly authored `SourceDelivery*`, `DeliveryQuest*`, quest state/codec and progression/currency state/planner files. It is not an executed qualification or a claim that save migration is implemented.

The present `QuestSnapshot.ValidateForAuthority` computes all accepted, unpaid rewards sharing each reserve and requires their sum to fit its balance. The acceptance planner constructs and validates the candidate obligation before returning success. Completion combines the delivered material candidate, reward candidate and completed participation before validating the remaining obligations. This is the intended conservation boundary; independent tests still need to establish both the insufficient-funding case and multiple explicitly funded actors.

The raw delivery planner sorts bounded, unique selections, requires their sum to equal the exact admitted bill, rejects protected/reserved or transformed inputs, retains source intervals, and reserves delivered lots. Full transfers retain their identities; partial transfers use distinct canonical selection ordinals. Touched storages and the custody snapshot advance once, and final production validation includes both raw and transformed capacity. The authority still must supply the composed world's identity checks; this primitive alone has no terrain, body or dialogue identity registry.

Two integration findings were sent to the coordinator while the code was still being composed:

1. **Conversation validation:** the initial quest planner accepted any supplied `DialogueSession` with matching listener/giver IDs. A caller could fabricate a matching record without admitted utterance, current speech/hearing or language evidence. The public boundary needs executable validation of the current admitted conversation, or a narrower trusted internal interface whose caller establishes it. A matching pair of actor IDs is insufficient evidence.
2. **Current command identity:** the delivery planner rejects a command identified as historically occupied, but `WorldStepProcessor` reserves current action IDs before interpreting them. Passing its ordinary `Occupied` callback directly would reject every valid completion. Preserve current-command reservation while separately checking every created child against the complete current and historical registry; do not globally exclude the current ID from collision checks on derived children.

The coordinator corrected the conversation gate to require exact membership in both `world.Dialogues` and the current working list. This is sufficient for the present one-action-per-actor batch: an actor cannot open its own conversation and submit a quest action in that same batch. Constructor admission already validates the committed record's speaker, utterance, time, reach, body and language. Static reinspection confirms this correction; fabricated, altered-cause and removed-working-conversation regressions have been authored and still await execution.

The independent [QuestCriticTests.cs](../../../Runtime/tests/OpenFantasy.Core.Tests/Quests/QuestCriticTests.cs) presently adds 13 unexecuted cases. They cover those three conversation variants, unauthenticated principal claims, overbooking, two explicitly funded player/host contributors, compound partial interval transfers, failure on the later derived child, four protection flags and an existing reservation. The second-contributor fixture explicitly admits its additional raw source, controlled corporeal resident, account and work state. The successful two-contributor scenario funds 400 units and a 12-unit project capacity; it does not invent funds during acceptance or claim a networked co-op qualification.

Static reinspection of profile-4 composition confirms the processor excludes its already-reserved current command from the historical predicate supplied to the raw delivery planner. The planner separately rejects a derived child equal to that command, and the processor reserves returned children against the complete identity registry. The independently authored test file now has 17 intended cases, adding composed success, historical child failure, a command/account collision and a reward/material definition alias. Execution and final source hashes remain pending.

## Hosting implementation ownership and current status

Later on 10 September 2026 UTC, the coordinator reassigned this critic to implement the concrete Hosting quest upgrade and its tests. The following is therefore **author implementation documentation**, not independent approval of that Hosting code. A different worker has been assigned its independent review. The earlier design and quest-core static findings remain attributed to the work actually performed.

`SqliteWorldAuthority.UpgradeProductionToQuests` now implements source-exclusive recovery, exact-head preparation, a consistent private backup, full old-row comparison, data-only migration in one foreign-key-enforced transaction, full staged replay, WAL checkpoint/close, and no-overwrite publication. `WorldUpgradePublication` shares the proven file-set admission, backup comparison, replay comparison and final publication guard between the production and quest upgrade paths. The old production table-rebuild transaction is unchanged. Quest admission adds no DDL, disables no foreign keys and leaves `user_version=3`.

The retained SQL migration kind is still numeric 3; its internal name is now `ProfileMigration`. `WorldProfileMigrationReplay` reads the canonical frame tag and dispatches exactly to production-migration v1 or quest-migration v1. Each selected decoder validates the complete frame and its version. Unknown tags, unsupported versions and corrupt payloads reject; there is no decoding fallback. Schema-3 genesis/head admission explicitly accepts profiles 3 and 4. New profile-4 genesis uses schema 3 without inventing a migration row.

The quest preparation writes the cause as identity kind 1, new pinned definitions as kind 5, and new accounts/project custodians/reservations as kind 4. The complete request, canonical outcome, before/after hashes and unchanged advancing-step ordinal are recorded together. Existing receipts, identities, checkpoints, usage and actual original genesis remain part of full replay. This does not implement checkpoint-tail acceleration or extend the existing development save-growth limits.

API coordination caught a concrete size mismatch: the first quest request proposal allowed 1 MiB, but the frozen schema admits at most 256 KiB in `accepted_batch`. The portable migration now caps the complete request at 256 KiB and initial admission at 255 KiB; larger admission rejects before publication. Hosting independently checks request/outcome bounds before staging. No SQL bound or historical encoding is widened.

The author added 27 intended Hosting cases in `QuestUpgradeTests.cs` and `QuestUpgradeRecoveryTests.cs`. They cover an actual gathered/crafted production history, prior exact receipts and migration bytes, data-only upgrade and reward completion/restart, source-file preservation, fresh genesis, interruption boundaries, early/late orphan sidecars, tampered migration family/tag/version/outcomes/identities/old receipts/checkpoints, rollback, stale heads, historical causes, insufficient acceptance funding and atomic completion faults. These tests are authored but **unexecuted** at this checkpoint. Existing production regression tests must also run after the shared publication refactor; no old pass is silently reused as proof for changed source.
