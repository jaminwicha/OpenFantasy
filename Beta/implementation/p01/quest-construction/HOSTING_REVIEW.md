# Independent Hosting quest-upgrade review

**Disposition: no blocking defect found in the reviewed bounded implementation.** This is an independent static review by the content/source worker, separate from the Hosting author's [persistence design and implementation account](PERSISTENCE_REVIEW.md). It reviews the new profile-three→four save continuation, its shared publication/replay changes, and the actual 27 authored Hosting cases. At this review boundary those cases had not yet executed. I ran no .NET build, native database or Godot process for this review; the coordinator owns execution. Exact reviewed source/test hashes are retained in [HOSTING_REVIEW.json](HOSTING_REVIEW.json).

The review covered `WorldQuestUpgrade`, `WorldQuestMigrationPreparation`, `WorldDatabaseQuestMigration`, the upgrade boundary hooks, `WorldUpgradePublication`, `WorldProfileMigrationReplay`, `WorldJournalRecovery`, public `SqliteWorldAuthority` upgrade/opening, migration-kind storage rows and the production migration's use of the new shared helper. The existing file-set, connection ownership, backup comparison, bounded journal policy and database write/read boundaries were checked as supporting context. The separate Core progression/quest rules and content admission are not represented as independently reviewed here.

| Concern | Static conclusion and actual authored cases |
| --- | --- |
| Correct source head | The source is opened under the existing exclusive local SQLite lease and completely recovered. Quest admission requires schema 3, and the pure processor requires the exact profile-3 world/branch/revision/steps/hash/source pin. Stale hashes and a historical command reused as the migration cause reject before publication. |
| Preserve earned history | The migration payload carries new admission only. The pure processor appends empty project storage/reservations to existing custody, while retaining actual production batches, source cursors, body/spatial state, residents, active dialogue and clocks. Hosting prepares one new commit with no actor-command receipt. The test fixture actually gathers twice, performs the previous production migration, crafts and opens dialogue before the new upgrade. Tests compare old journal/receipt/identity bytes, gathered/production component hashes, source files and reopened state. |
| Backup and publication ownership | The shared helper makes a private staging copy beside the destination, compares all original retained rows, then verifies complete candidate replay before checkpointing, closing and moving the staged main file. The source remains owned for that operation. The corrected whole file-set guard checks main, WAL, SHM and rollback-journal paths both at entry and after the final prepublication hook. No overwrite or automatic fallback path was introduced. Six new cases inject initial/late sidecars; five interruption cases cover backup, transaction and publication hooks. The original sidecar regression suite remains required after the shared-helper refactor. |
| One database transaction | New migration row, complete head, admitted definitions/entities and any scheduled checkpoint are written in one transaction. This is a data-only schema-3 operation; FK enforcement stays enabled and schema metadata does not change. An injected precommit failure checks rollback of head, identities and journal. Completion has separate before/after-commit cases proving the expected whole reward/project state on reopen. |
| Strict replay dispatch | Stored kind 3 remains the same numeric migration kind. Its canonical tag selects one known production or quest decoder, with no fallback after decoder failure. The dispatcher bounds the frame/tag before slicing; the selected strict decoder handles the rest. Replay recomputes and compares exact request/outcome bytes, hashes, head, identity roles, receipts and checkpoints. Unknown tag, unsupported version, wrong migration family, altered outcome, missing/changed identities, removed old receipt and unscheduled checkpoint are distinct mutation cases. |
| Historical identity retention | Preparation asks the processor to check current, genesis and stored historical identities. Newly introduced definitions and instances are separately reserved at the migration sequence; the migration cause retains its own role. Recovery independently reconstructs and compares the complete identity table. It does not infer that an identity became reusable when its last live lot disappeared. |
| Finite funding and idempotence | The stored admission contains finite balances and the exact new quest obligation. The main journey checks one 200-gil debit/credit, level 3/residual XP 38, reserved six-wood project stock and unchanged production after completion, then reopens and retrieves exact old/new receipts. A changed retry payload rejects. A deliberately underfunded 199-gil admission yields a durable rejected acceptance without an unpaid promise. These are small fixture proofs, not source-content or networked co-op qualification. |
| Recovery limits | The previous full-replay usage and checkpoint counters carry forward. Migration consumes another commit and accepted byte budget without adding simulation time or resetting the development envelope. The retained 250,000-commit/65,536-outcome/128-MiB accepted-journal limits remain stop conditions. No checkpoint-tail or long-campaign scaling claim follows from these tests. |

The old schema-three DDL, production schema transaction and production migration codec were unchanged at review; the old production test's only edit is the enum label from `ProductionMigration` to `ProfileMigration`, whose serialized value remains 3. The public new-genesis path accepts profile 4 under schema 3, and its separate authored test verifies no invented migration rows. Normal `OpenExisting` performs validation/replay and does not silently upgrade or choose an older save.

The new cases total **27**: crafted-history/receipt/reward round trip (1), upgrade interruptions (5), initial/late sidecars (6), direct profile-4 genesis (1), corruption mutations (9), transactional rollback (1), stale/historical/path conflicts (1), underfunded acceptance persistence (1), and completion commit interruptions (2). They are concrete runtime tests, not assertions that a planned API exists. Execution must still establish that they compile and pass, alongside the older production/sidecar cases affected by shared publication code.

Retained limits are explicit: the two actors and small fixture are not multiplayer transport tests; new progression is an authored admission rather than restored unrepresented old stats; exhausted finite wood may make a newly offered quest unavailable; the old source copy is a recovery copy and does not authorize independently advancing two copies without a branch policy. Injected application exceptions do not qualify sudden power failure or every target filesystem/platform. This review does not claim real construction, final art, production-scale replay or user acceptance.
