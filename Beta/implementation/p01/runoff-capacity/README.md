# Shared runoff capacity ownership

This increment connects funded runoff projections to one finite reservation owner. Several budgets
can no longer each promise the same headroom, and real custody/Production changes must reconcile
with the outstanding obligations before the composed candidate can be published.

## Implemented scope

The immutable owner supports sixteen pending commitments over one exact network, mapping, material,
owner and receiver profile. It shares complete counted authority and optional Production. Incoming
obligations are summed with existing raw/derived occupancy against both counted and calibrated physical
capacity. Disjoint time intervals do not imply reusable space; outgoing promises do not subtract stock.

Admission, capacity cancellation and reconciliation use complete-state plans and a separate logical
revision. Cancellation keeps a non-reusable identity and leaves actual source reservations unchanged.
An explicit custody successor may release source stock afterward. Empty owners retain their domain,
physical calibration and closed identities. The closed set is bounded to 4,096 admitted reservation IDs;
exhaustion rejects rather than dropping history. Production mode/recipes and exact prior batches persist.
Every active input is re-prepared and all receiver obligations are checked against a reconciled candidate.

The normalized v1 archive stores the shared network/authority/Production once, with forcing rows, closed
identities and rederived receiver witnesses. The new host inspector and maintained verifier hook exercise
this standalone contract. Existing runoff row codecs and scope validation are shared without changing the
old runoff archive. Application classes remain modular, immutable and object-oriented.

and material reference explain the publication boundary, byte layout, invariants and limits.

## Remaining integration

This is ownership inside a standalone compositor. A durable world publisher must exclusively admit the
owner and route all affected mutations through it; another independent owner cannot reserve the same
receiver. The archive/operator does not publish a lived world, authenticate player commands, settle
runoff, create reservoir shape or advance time. There is no gameplay or visual change in this increment.

Next dependencies include physical source/buffer/receiver geometry and supported liquid storage;
complete crust/climate/coast macro admission; staged arrival/backpressure and topology/Wait/history
revalidation; and retained local terrain/allocation/world ownership. Heterogeneous fluids, cross-network
composition and reservation/history compaction need explicit contracts. Native/rendered journeys and
combined maximum workload performance were not rerun. All full phase and production gates remain open.
