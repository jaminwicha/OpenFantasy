# Portable core integration: gather → rations → Wren → windbreak

The retained portable core can support this sequence through one authority, but the present production definitions are not an executable crafting or construction engine. The smallest sound continuation is the implemented finite gathering increment, then explicit material transformation, then quest/reward and construction transactions. Keeping those seams typed avoids inventing source rights or breaking canonical saved-world compatibility. This is a bounded implementation review; it does not freeze every future crafting or structural rule.

[CORE_CONTRACT.md](CORE_CONTRACT.md) describes implemented gathering. [SOURCE_CONTRACT.md](SOURCE_CONTRACT.md) distinguishes source behavior from authored changes, including the important fact that the source Wren quest removes wood and grants rewards but never constructs a windbreak.

## Reusable application contracts

| Existing API | Direct use and limit |
| --- | --- |
| `CountedAuthorityState`, `AdmittedCountedSource`, `CustodianStorage`, `SourceInterval`, `CountedSourceLot` | Exact controlled custody, finite source capacities and nonoverlapping untransformed claims. Unissued source stock is permitted. Source intervals must not be reused after harvesting, transfer or future consumption. |
| `CustodyTransferPlanner.Plan` | Moves or splits already issued lots; it is not a gathering extractor, ingredient consumer or crafted-output provenance constructor. Direct node extraction now uses an admitted source cursor instead of a fictitious hidden actor. |
| `MaterialDefinition`, `MassMilligrams`, `VolumeMicrolitres`, `HardnessRating`, `MaterialCatalog` | Finite per-unit physical definitions and exact version lookup. Importing counted source wood does not decide its kilograms, volume, hardness, shape or one-cell build coverage. |
| `MaterialRecipeDefinition(PackageId, DefinitionId, key, RequiredWork, SourceRecipePayloadHash, catalog, terms)` | A bounded ordinary-material input/output/waste transform with checked exact mass accounting. It validates definitions and conserved mass; it does not run crafting, source transformations, storage placement or aggregate occupied volume. |
| `WorkUnits` | An abstract positive integer measure used by recipe definitions. There is no production-work runtime or accepted conversion to advancing steps/calendar time. The illustrative 120 work value is not imported source tuning. |
| `DueWorkQueueSnapshot`, `SelectDue(cutoff, phase, max)`, `ApplySelection` | An immutable bounded calendar-only queue with explicit selected-work acknowledgment. Useful for future passive process transitions when composed into the same world transaction. It is not integrated into the current world root, is not durable by itself, and must not compare calendar milliseconds with gathering effort or tactical units. |
| `TerrainRegionSnapshot.Excavate` | Atomic bounded whole-cell removal, retaining substrate source/formation identity. It does not yield an item, charge work, model structural support, or place a solid structure. Reversing excavation is not a construction API. |
| `LocalSpatialSnapshot`, body condition, resident/control/language joins | Real actor clearance, shared player/NPC action applicability and locality. Construction must preserve these invariants and reject entombing actors or invalidating required support. |
| `WorldSnapshot`, `WorldStepProcessor`, `WorldActionReceipt`, SQLite world authority | One typed immutable root, action-first ordering, explicit fixed-step clock, reading holds, identity reservation, atomic journal/state/receipt persistence and replay. New gameplay should extend this route rather than create a client-side authority or independent save sidecar. |

## Smallest retained sequence

**1. Finite gathering — implemented increment.** The new optional component admits two exact source-yield nodes, real finite axe/sickle lots, all actor work state and explicit source capacities. It spends the banked Squire-derived readiness profile and issues exact untransformed intervals, with range/body/tool/capacity/access checks. Regrowth never resets source rights. The parent integrates native input, projection and SQLite durability. It deliberately does not claim biological ecology, source-density population, tool wear or a playable crafting loop.

**2. Actual ration transformation — next contract prerequisite.** Preserve the original counted recipe `2 berries + 1 wood → 2 rations`. Its source payload hash is `c384027c76855ade482105233cadd07ea930a265f73e12beab852de1cc756491`. This source payload hash remains distinct from a new authored runtime recipe version. The source is instantaneous and provides neither physical measures nor waste or required work. The P00 physical recipe is an illustrative authored calibration with residue and positive work; it must not silently become gameplay balance.

A real command must identify the recipe version, actor, current input lots and revisions, destination and explicit applicable station/tool/body requirements. First reserve/check every input and output-placement constraint. In one candidate, retain input-consumption history and mint a deterministic transformed batch whose lineage names all consumed source subintervals, exact recipe/process pin and each allocated output/waste share. Ensure those consumed claims cannot also remain in active inventory, be consumed twice, or be reminted as independent source admission. `CountedSourceLot` explicitly represents one untransformed interval, so a mixed ration cannot be laundered into that type by attaching a new source ID or a recipe hash alone. A small typed transformed-lot/provenance family and its exact codecs are required; do not build an unrestricted generic process graph to execute one recipe.

Define physical meaning before using existing mass validation: is wood fuel, packaging or ingredient; does heat/material leave as waste; what constitutes one unit? Output volume need not equal input volume, but all products/totals/storage capacity must use checked arithmetic or an explicit qualified wider representation before physical lots exist. If timed work is desired, pin an authored work-to-time/effort rule, owned work state, interruption/cancellation/resource refund policy and exactly-once completion. Do not use wall-clock delays or infer 120 work means 120 simulation ticks. An instantaneous faithful counted transform is a coherent first gameplay choice once provenance is executable.

**3. Wren acceptance and turn-in — state and reward prerequisite.** Preserve actor-owned quest acceptance, giver/range/minimum-level checks, six currently held wood, once-only completion and exact 420 XP/200 gil obligations. Current inventory handover is not quest acceptance/completion. Earlier gifts should not retroactively satisfy the quest without an explicit design choice. The original quest accepts legal initial/purchased/gathered wood; the validation journey can require exercising gathering without changing that source rule. Currency and XP/level-up need actual portable state and deterministic changes before reporting their rewards as fully implemented. If those pieces are phased separately, retain the unresolved obligation visibly in implementation scope rather than expose fake counters.

**4. Persistent windbreak — explicit authored extension.** Introduce a concrete structure/site definition, footprint, material bill, controlled builder, progress/work and exact placement prerequisites. Move or reserve the six contributed wood into structure/project custody so source claims remain traceable. Retain installed material identities rather than equating one counted wood with one full solid terrain cell. Validate site permission, footprint collisions, full body clearance, direct support and accessible approaches before publication. On completion publish the structure state, occupied geometry and materials in one transaction. Dialogue claiming protection should follow actual completed construction; actual crop/wind effects remain another implemented requirement. Wren can execute work using their own admitted control and custody through the same processor. A player cannot spend private NPC stock simply because the NPC is nearby.

## Version and semantic hazards

- Existing world profile-one canonical bytes and hashes must remain stable. Root dispatch chooses explicit profile-one or profile-two codecs; absent gathering is not a silently appended empty block. SQLite schema version two, OFC framing version one and gathering component version one are separate contracts.
- A new content admission creates an explicit distinct genesis and identity lineage. It must not opportunistically populate tools, resources, gauges or future quest ledgers when reopening an old world. Future genuine migration requires pinned source/target versions, complete state conversion, backup/recovery and deterministic migration evidence.
- Source respawn ticks map to committed advancing steps, not game milliseconds. With present pacing, 900 steps are 45 active seconds and 27 game minutes; holds/offline time contribute zero. Source random relocated/new-ID respawn is intentionally replaced by finite fixed-site identity-preserving cycles.
- Construction and crafted-output consumption require permanent lineage. Deleting live lots cannot stand in for a consumed-right ledger; adding fresh `AdmittedCountedSource` rows cannot manufacture replacement export rights.
- Recipe IDs and hashes are content identity, not authorization. Owner/session checks and current committed revisions remain required before private state inspection. UI animations, timers, projected totals and dialogue never manufacture work completion or inventory.
- New trait/skill/technology complexity should compose only when it changes executable rules. The first ration transform and windbreak should not depend on a speculative universal graph, fluid solver, labor market or NPC planner.

## Required incremental proofs

Gathering proofs are in the new core/hosting tests and native validation evidence. The next crafting tests must reject duplicate/overlapping ingredients, wrong pins/stale revisions, owner/reservation violations, insufficient input or output capacity and mixed-source relabeling; prove exact counted recipe results, conserved declared mass/waste, deterministic lineage and no partial consumption. Timed work additionally needs interruption, pause/hold, replay, duplicate completion and arithmetic-boundary cases.

Quest tests must prove correct acceptance, minimum progression, current six-wood readiness, crafted wood consumption competing with turn-in, remote/wrong giver, once-only reward and replay. Construction tests must prove simultaneous material/site revision conflicts, no entombment, no blocked required approach, supported footprint, retained source custody, rollback of failed placement, actual completed geometry and reopen/replay equality. The connected retained playthrough is gather berries/wood → create two actual rations → fund a different six wood → complete the quest's real reward → build an actual persistent windbreak, all through the same portable authority. Only mark each stage complete after those behaviors exist.

This review inspected repository implementation and frozen source evidence. It did not run external research or a concurrent build. Final source hashes and executed validation are retained alongside the implementation; future feature proposals above are not claims of existing gameplay.
